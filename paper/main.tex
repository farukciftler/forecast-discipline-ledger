\begin{abstract}
Agent evaluation is usually episodic: a task is attempted once and scored.
We study a different setting. For three calendar months a language-model agent
ran a live measurement process under human supervision: a forecasting ledger
that writes dated, sealed, pre-registered predictions for \NumForecastAssets{}
financial assets and scores them against realised outcomes. Alongside the
forecasts, the process kept a structured log of every operational error the
agent made, recording its class, the mechanism that caught it, \emph{who}
caught it, and how many days it stayed hidden. We release both datasets as a
frozen snapshot.

The forecasting results are negative, as the pre-registration allowed them to
be. In the primary pool the agent beats all three baselines at once in
$\BeatAllK/\BeatAllN = \BeatAllRate$ of rows and on \DayAllWon{} of \DayAllN{}
forecast days. Its $80\%$ intervals cover $\CovRate$. Its up-move
probabilities show no skill once a single policy-driven asset is set aside.

The error log is the more unusual object. Of \ErrN{} records, $\RepRate$ repeat
an earlier one. Median detection latency is \LatMedian{} day, the mean
\LatMean{} and the maximum \LatMax{}, and the pre-registered test finds no
decline in latency over the period. We name a recurring failure mode of
agent-maintained systems: the agent writes a correct rule into its own
documentation and then does not follow it, because \emph{documentation is not
a mechanism}. The clearest instance went unenforced for \KNineThreeLat{} days.
The most persistent is the daily routine itself, which has no trigger of its
own and did not run on \OpenMissed{} of \OpenDays{} market days. The log is
written by the agent that made the errors, so errors it never noticed are
absent by construction; we describe a capture--recapture design that would
make that population estimable.
\end{abstract}

\section{Introduction}

Most published evaluation of language-model agents is \emph{episodic}. A
benchmark presents a task, the agent attempts it, and the attempt is scored.
This design answers ``can the agent do X?'' It does not answer a question that
matters more once agents are deployed: \emph{what happens to a system an agent
maintains for months, and how do its failures surface?}

Answering that requires a task benchmarks usually cannot provide. It has to
run continuously, so that errors have time to compound or to be caught. It has
to carry consequences, so that the agent has something to be wrong about. It
also needs a human in the loop, because without someone who occasionally
notices what the agent missed, self-report cannot be checked at all.

This paper studies such a task over a fixed three-month window and releases
the data. The agent maintains a forecasting ledger over \NumAssets{} financial
assets, \NumForecastAssets{} of which are forecast. On each run it records
point forecasts, $80\%$ intervals and up-move probabilities at 1-day, 1-week
and 1-month horizons, before outcomes are known. A deterministic engine seals
and scores them. The analysis plan was pre-registered, and protocol changes
increment a version number so that observations produced under different rules
are never pooled.

Our contribution is not a forecasting method. The forecasting results are
null, and we report them as such. The contribution is the \emph{operational
telemetry} collected alongside: a structured record of every mistake the agent
made while running the process, with detection latency and attribution.

\paragraph{Contributions.}
\begin{enumerate}
  \item A released, anonymised, longitudinal dataset of language-model agent
        operational errors with detection mechanism, detecting party, and
        detection latency in days (\S\ref{sec:errors}).
  \item Pre-registered null results on short-horizon forecasting, with every
        pre-registered hypothesis either tested or reported as below its
        minimum sample (\S\ref{sec:forecast}).
  \item A named failure mode, \emph{rules written but not mechanised},
        illustrated by three clear instances and two adjacent ones
        (\S\ref{sec:mechanism}).
  \item A design that would make the unobserved error population estimable
        instead of merely acknowledged (\S\ref{sec:future}).
\end{enumerate}

\section{Related work}\label{sec:related}

\paragraph{Agent evaluation is episodic.} Benchmarks such as
SWE-bench~\cite{jimenez2024swebench} present a task, let an agent attempt it,
and score the attempt. The design is well suited to measuring capability and
poorly suited to measuring what happens to a system an agent tends over time.
An agent that scores well on isolated tasks may still degrade a system it
maintains, and the degradation is invisible to a benchmark that never runs
twice on the same artefact.

Continuing deployments do exist and are reported. Williams et
al.~\cite{williams2026pomona} ran Pomona, an agent that opens small repair
pull requests, for three months inside Bloomberg and evaluated it with a
survey of senior engineers. Their framing is close to ours in one respect and
opposite in another. It is close because their stated aims are reducing
technical debt and keeping engineer trust, the two things a maintained system
runs on. It is opposite because they measure what the agent produced and we
measure what it got wrong. Their unit is the accepted pull request; ours is
the logged mistake, its detection latency, and who caught it.

\paragraph{The human in the loop is a cost, not a free correction.} Our
process has a supervisor who catches what the agent does not, and \ErrHuman{}
of \ErrN{} records were found that way. It is tempting to read that as
reassurance. Garousi~\cite{garousi2026oversight} argues the opposite and we
think he is right: reviewing and reworking what an agent produces is neither
optional nor free, and the volume of suggestions imposes a cognitive load of
its own. A supervision rate is therefore a cost figure as much as a safety
figure. We cannot separate the two here, for the reason given in
\S\ref{sec:limits}: the log does not record whether the agent would have
caught what the human caught.

\paragraph{Forecast scoring.} The scoring apparatus is standard. Proper
scoring rules and their decomposition are treated by Gneiting and
Raftery~\cite{gneiting2007scoring}; the probability score itself dates to
Brier~\cite{brier1950}. We add nothing to this literature: we use it as
instrumentation and report that it returns a null. The practice of scoring
dated judgements against baselines, and of taking the comparison and not the
raw hit rate as the unit of evidence, follows the forecasting-tournament
tradition described by Tetlock and Gardner~\cite{tetlock2015}.

\paragraph{Pre-registration.} Fixing the analysis plan before the data is seen
is the standard defence against selective reporting~\cite{nosek2018prereg}. It
is normally applied to a study with a planned end. Here it was applied to a
running process, which raises a question the literature does not settle: what
counts as a pre-registration when data accrues daily and hypotheses are added
as the process reveals them. We version the protocol, split the pool at every
rule change, date every amendment, and mark anything added after the fact as
exploratory. That is a convention we adopted, and we make no claim that it is
the right one.

\paragraph{Latent conditions and incident analysis.} The pattern we name in
\S\ref{sec:mechanism} is a close relative of Reason's \emph{latent
conditions}~\cite{reason1990}: a defect introduced long before the failure it
enables, dormant because nothing exercises it. The difference is the author.
In Reason's account latent conditions are left by designers for operators to
trip over. Here the agent is both, and writes the very rule it will later fail
to apply.

\paragraph{Technical debt.} The same mechanism has an older name in software
engineering. Behutiye et al.~\cite{behutiye2017td}, reviewing technical debt
in agile development, report that the management strategies recurring most in
the literature are refactoring and \emph{increasing the visibility of the
debt}, and that pressure for quick delivery is among its most common causes.
Both map onto what we see. A rule that is written down but never wired into
the process is debt of exactly this kind: the cost is deferred, it accrues
quietly, and it is paid in repeat failures. Our latency field is a visibility
instrument in their sense, since it measures how long a defect survived
unnoticed and not how many defects there were. The Dagstuhl manifesto on
reframing technical debt~\cite{avgeriou2025reframing} names tooling and data
collection among the places current practice falls short. Our records are a
small instance of both shortfalls at once: the rule that went unenforced was
written in a document no tool reads, and its cost is visible only because the
log happened to carry a latency field.

\paragraph{What we did not find.} Longitudinal agent deployments are reported,
as~\cite{williams2026pomona} shows. What we did not find is a released dataset
from one of them recording the agent's own operational failures with detection
latency and attribution, nor work applying capture--recapture to estimate an
agent's unobserved error population. The gap is narrow and we state it
narrowly: it is not that nobody runs agents for months, it is that the failure
data those months produce stays inside the organisation that collected it.

\section{Setup}\label{sec:setup}

\paragraph{The task.} A daily routine over \NumAssets{} assets, pseudonymised
\texttt{A1}--\texttt{A8}: collect prices from machine-readable sources, record
a market-state snapshot, resolve forecasts that have come due, scan the day's
news, write new forecasts, and commit. A fixed engine performs the steps that
must be deterministic, and the agent performs the ones that need judgement.
The engine never fetches data and never writes a forecast. The agent never
computes a score. The split is deliberate: arithmetic must not hallucinate,
and neither must data collection.

\paragraph{What is recorded.} Every forecast carries a point estimate, an
$80\%$ interval, an up-move probability, a stated confidence, the evidence
items it was derived from, and an invalidating condition. Resolution is
automatic against the realised value and against three baselines: \emph{naive}
(no change), \emph{drift} (mean of the last five observed changes) and
\emph{momentum} (the last observed change). All three use only information
available at forecast time.

\paragraph{Pre-registration.} The analysis plan fixes, in advance, which
hypothesis is primary, which test is applied, the minimum $n$, and the
reporting order. Findings outside the plan are labelled exploratory and are
not counted as evidence. Rule changes increment a protocol version, and rows
from different versions are not pooled.

\paragraph{Study period.} This paper analyses a closed window, \WindowStart{}
to \WindowEnd{}: three calendar months, \WindowCalDays{} days. The start is
the ledger's first day. The end date was fixed when the manuscript was
prepared, as the last day of the third calendar month, and was not chosen by
inspecting results. We state this because a window selected after the fact is
a forking path, and the reader is entitled to weigh the forecasting results
with that in mind. A row enters the release only if the forecast was written,
its target date fell, and its outcome was observed inside the window.
Forecasts whose outcomes arrive later appear as unresolved.

\paragraph{Coverage of the window.} The local market was open on \OpenDays{}
of the \WindowCalDays{} days. The routine ran on \OpenCovered{} of them and on
\ClosedCovered{} further days when the market was closed, for \NumDays{}
forecast days in total (\FirstDay{} to \LastDay). It did not run on
\OpenMissed{} market days. The longest gap is \MissRunMax{} consecutive market
days and it sits at the very end of the window. We return to these gaps in
\S\ref{sec:mechanism}, because they are an instance of the paper's subject and
not only missing data.

\paragraph{Pools.} \NumWritten{} forecasts were written. Of these,
\NumResolved{} were resolved inside the window, and \NumDirty{} of the
resolved rows are flagged and excluded: their target day was a market day on
which no snapshot was taken, so they were resolved against a later price and
no longer measure the stated horizon. That leaves \NumScoredAll{} scored rows.
The pre-registration then removes two groups from any skill claim. One-month
outputs are \emph{projections}, declared unmeasurable in advance
(\NumProjection{} rows). Rows written under the three earlier protocol
versions are not pooled with the current one (\NumEarlierProto{} rows). The
\emph{primary pool} is what remains: \PrimaryN{} rows at the 1-day and 1-week
horizons under protocol version \LatestProtocol{}, written on \PrimaryDays{}
forecast days. Table~\ref{tab:pools} reports the excluded versions separately.

\paragraph{Models.} \NumModels{} versions of the language model produced
forecasts during the window, pseudonymised \modelA{} to \modelD{}. The primary
pool mixes three of them. The pre-registration did not anticipate a model
change, so we report the split in Table~\ref{tab:pools} and do not treat the
pooled figure as a property of any one model.

\paragraph{H1: the agent does not beat the baselines jointly.}
Table~\ref{tab:baselines} states the central negative result. Taken one at a
time, every baseline is beaten. Taken together, they are not: the agent beats
all three on $\BeatAllRate$ of rows and on \DayAllWon{} of \DayAllN{} forecast
days. Each baseline has a regime in which it is easy to beat. A zero-change
forecast loses to any small positive one when more moves are up than down, as
$\BaseRate$ of scored moves here were, and a last-change forecast loses
whenever moves do not persist. The joint criterion was fixed in advance so
that no single weak baseline could carry a headline.

\paragraph{What the single-baseline wins probably are.} The funds in the
ledger publish their price one day late. A ``1-day forecast'' of a fund is
therefore written after the session it will be priced on has partly or wholly
traded, and the agent can see that session's public markets. A forecast built
that way will tend to beat a zero-change baseline and will narrow the error
spread relative to the sample mean. The released reproduction script shows the
narrowing for the funds and not for the spot asset. The pre-registration anticipated
this (H12) and calls it delayed accounting, not forecasting. We did not
separate the two pools here, so we draw no conclusion from the single-baseline
rows beyond the one the joint criterion already gives.

\paragraph{H2: intervals are too wide.} Coverage is
$\CovK/\CovN = \CovRate$ (Wilson $95\%$ interval $\CovLo$--$\CovHi$) against
an $0.80$ target; the exact two-sided binomial test gives $p = \CovP$. One
asset is a foreign-currency deposit under a managed exchange rate, whose
intervals are almost never breached (\CovFxK{} of \CovFxN). Without it
coverage is $\CovExFxRate$, so the finding does not depend on that asset.

The pre-registration says that a significant H2 result leads to a corrected
interval rule. It was amended, before the correction was made, to measure the
candidate rule first: a \emph{shadow} interval built from empirical quantiles
of the past $250$ trading days is written beside 1-day forecasts and never
scored. On \ShadowN{} matched rows (minimum $100$) the shadow interval covers
$\ShadowCov$ where the standing one covers $\ShadowStandingCov$, at
$\ShadowWidthRatio$ of the width. The amendment also recorded a prediction
before any shadow data existed: the new rule would lower coverage to about
$0.84$--$0.85$ and would not reach $0.80$, because the excess is mostly the
calm of the sample and not the rule. The direction and the failure to reach
target both held; the level came out slightly above the predicted range. The
amendment's second condition for switching, that a more volatile regime be
observed first, was not met inside the window: the largest fall in the spot
asset between consecutive observations was $\AoneMinRet\%$ against a threshold
of $-3\%$, and the implied-volatility index it names closed above $30$ on
\GvzAboveThirty{} of \GvzDays{} recorded days. The standing rule was therefore
kept for the whole period.

\paragraph{H3: one row short.} The single pre-registered subgroup restricts H1
to forecasts the agent marked as medium or high confidence. It holds
\HThreeN{} rows against a pre-registered minimum of $100$, so it is not
tested. Descriptively, \HThreeK{} of those rows beat all three baselines.

\paragraph{Probabilities: a positive score that is not skill.} The
pre-registered statistic for the up-move probability is the Brier skill score
against a running base rate. Mean Brier score is $\BrierModel$
($n=\BrierN$). Against a base rate walked forward over resolved rows the skill
score is $\BSSWalk$; against the full-sample rate of $\BaseRate$, a
look-ahead and therefore a harder comparison, it is $\BSS$. Both are positive.

We do not read either as skill, and the reason is in the data. The
managed-rate asset rose on \FxUp{} of its \FxN{} scored rows, and the agent's
mean probability for it was $\FxMeanPup$. A pooled base rate knows nothing
about which asset a row belongs to, so simply knowing that one asset drifts
upward by policy beats it. Two checks, neither of them pre-registered and both
therefore exploratory, remove that information. Excluding the asset leaves a
skill score of $\BSSExFx$. Scoring every row against its own asset's base rate
gives $\BSSOwnBase$. The stated probabilities and a constant forecast at each
asset's base rate score about the same.

\paragraph{Power.} These figures overstate the evidence. The assets move in
correlated blocks: the two foreign-equity funds have a return correlation of
$\CorrAtwoAthree$, and two precious-metal instruments track the same
underlying. A Kish-style effective count, $k^{2}/\sum_{ij}\rho_{ij}$, gives
$\NEff$ effectively independent series where \NumForecastAssets{} are
forecast. The day-level tests in Table~\ref{tab:baselines} are the more honest
ones for that reason. With \PrimaryDays{} forecast days, no forecasting
conclusion here should be read as more than ``not demonstrated''.

\paragraph{Two features stand out.} First, latency is skewed. The median is
\LatMedian{} day while the mean is \LatMean{} and the maximum is \LatMax{}
days. Routine cross-checking catches most errors within a day, and a minority
survive it for weeks. The tail is bounded by the window: the maximum says how
long one error did hide, and nothing about how long an error \emph{can} hide.
Second, close to half of the records ($\RepRate$) repeat an earlier one. The
agent returns to failure classes it has already documented, and writing a
failure down did not prevent its recurrence. There is no control arm, so this
rate has nothing to be compared against.

\paragraph{H7: latency does not fall over time.} The pre-registered test is a
Spearman rank correlation between record order and latency, with the
prediction that latency falls as the process matures. Over \SpearN{} records
(minimum $120$) the correlation is $\SpearRho$, with a one-sided $p$ of
$\SpearP$ for a decline. The hypothesis is not supported. One bias runs
against it and should be stated: an early record cannot have a long latency
because the ledger was young, so the correlation is pushed upward by
construction. The data cannot distinguish that artefact from a real absence of
improvement.

\paragraph{H8: not run.} The pre-registration specifies a $\chi^{2}$ test on
the mechanism-by-class table with at least five expected records per cell
after grouping, and does not specify the grouping. With \ErrN{} records spread
over eighty cells, some grouping is unavoidable, and choosing one now would be
choosing it after seeing the table. We report the omission as a defect of the
pre-registration and do not run the test.

\paragraph{H9: self-correction is not shown to favour the agent.} Of the
records whose effect on the ledger's own scores was classified, \EffFav{} were
favourable to the agent and \EffUnfav{} unfavourable. That is \EffN{}
directional corrections against a pre-registered minimum of $40$, so the test
is not run; the two-sided exact $p$ would be $\EffP$, with a favourable share
of $\EffFavShare$ ($95\%$ interval $\EffLo$--$\EffHi$). This is the one
hypothesis here for which a \emph{significant} result would have been bad
news: a skew toward self-favouring corrections would indicate that corrections
are chosen after seeing which way they cut. The observed imbalance leans the
other way.

\section{Rules are not mechanisms}\label{sec:mechanism}

One recurring pattern is specific enough to name. The agent diagnosed a real
problem correctly, wrote the correct rule into its own documentation, and then
did not apply it. A document is not an enforcement point.

We are deliberate about the count. Three entries in Table~\ref{tab:mechanism}
are clear instances: a documented rule existed, nothing enforced it, and the
omission had a cost. Two further records are adjacent but weaker. One is a
missing validation and not an unfollowed rule; the other is a wrong causal
diagnosis that was later corrected. We list all five and mark which is which,
and we do not report ``five instances'' of a category stretched to fit.

\paragraph{The cost is measurable.} A documented interval-recording rule was
followed on the day it was written, ignored for the next three days, then
resumed when someone happened to remember it. Those three days cannot be
reconstructed after the fact, so the pool they were meant to fill is
permanently short by three observations.

\paragraph{The routine itself is the largest instance.} The process has no
scheduler. A run starts when the supervisor opens a session, and the rule that
it must happen daily lives in the operating document. The log shows what that
arrangement costs. Records \SkipChainFirst{} to \SkipChainLast{} form a chain
of \SkipChainN{} entries, \SkipChainAgent{} of them found by the agent on a
later run, all within \SkipChainLatMax{} days, each restating that the day was
lost and cannot be recovered. Detection was fast every time and changed nothing, because the
thing detected was an absence that only a trigger could have prevented. The
window then ends with \MissRunEnd{} consecutive market days on which the
routine did not run at all. This instance differs from the first two in one
respect that matters for attribution: the party who had to remember was the
human supervisor, not the agent in the middle of a task. We count it as clear
because the structure is identical. A rule was written, repeated
\SkipChainN{} times, and never given a mechanism.

\paragraph{Why this should generalise.} The pattern does not depend on the
particular agent or task. It depends on a structural asymmetry. An agent that
writes its own operating documentation is also its main reader, and nothing
enforces reading. A rule that survives only as prose therefore depends on
someone remembering it at the moment it applies, which is the moment that
someone is busy with whatever caused the rule to be written.

\paragraph{An exploratory comparison, and why it is not evidence.}
We expected errors of \emph{absence} (a missing field, an unenforced rule) to
hide longer than errors of \emph{wrong value}, since a wrong number can be
cross-checked against another number and a missing one cannot. Records in the
two absence-like classes ($n = \AbsN$) have median latency $\AbsMedian$ days
and mean $\AbsMean$; the remainder ($n = \OthN$) have median $\OthMedian$ and
mean $\OthMean$. A Mann--Whitney comparison gives $z = \MWZ$, two-sided
$p = \MWP$. The medians are equal and the difference lives entirely in the
tail.

We report the number and decline to call it a test. The hypothesis was formed
after seeing the latency distribution, and so was its operationalisation:
``absence-like'' is not a field in the log but a grouping of two of the eight
error classes, chosen after looking. With eight classes there are $2^{8}$
possible groupings, and nothing constrained the choice except the shape of the
data. A comparison whose hypothesis, grouping and direction are all selected
post hoc has no interpretable $p$-value, and a value below $0.05$ is least
informative in exactly this situation.

\section{Limitations}\label{sec:limits}

\paragraph{The log is self-reported.} It is written by the same agent that
made the errors. Errors the agent never noticed are absent by construction,
and no internal analysis recovers them. The \ErrHuman{} human-detected records
hint at a miss rate without estimating one, because the log does not record
whether the agent would have caught what the human caught.

\paragraph{Self-categorisation, not just self-report.} The agent also chose
the error classes, designed the controlled vocabulary they belong to, and
decided which records count as instances of the pattern in
\S\ref{sec:mechanism}. That section marks two of five instances as merely
adjacent for this reason, but the marking is itself the agent's judgement.

\paragraph{Classification is partly retrospective.} The controlled vocabulary
was introduced after \VocabFreezeN{} records had accumulated, and those were
mapped to it after the data was visible. The released log can therefore be
split into an exploratory pool and a confirmatory pool of \ConfirmN{} records
that begins where the vocabulary was fixed. The class-based comparison in
\S\ref{sec:mechanism} uses all records and is exploratory for that reason as
well.

\paragraph{The pattern recurred in the log itself.} While auditing an earlier
draft of this manuscript we recomputed every latency value from the two dates
that define it. Three disagreed with the stored figure. Two were off by a day.
One, the record used above as the clearest example of the pattern, stored
\emph{four hundred} days where the arithmetic gives \KNineThreeLat. The value
had been entered by hand, the field is derivable, and no check existed. A
latency of that size was impossible on its face, since no record can be older
than the ledger. Neither the agent that wrote the figure nor the human who
reviewed the release noticed. The operating document already stated that
latency equals the logged date minus the event date. It was written down, it
was correct, and it was not enforced. The error reached the published
dataset and three archived releases before it was caught; those archives
cannot be edited, and the correction is stated in the revision notes and
here. A check now fails the
daily run if any latency disagrees with its dates.

\paragraph{The forecasting pools carry two caveats.} The window's end date was
fixed when this manuscript was prepared, as described in \S\ref{sec:setup}.
And the primary pool mixes three model versions, because the pre-registration
did not foresee a model change.

\paragraph{Single agent, single task, small $n$.} One agent family, one task,
one supervisor, \NumDays{} forecast days. Nothing here establishes a rate that
transfers to other agents. The dataset's value is that it exists and is open,
not that it is representative.

\section{Future work}\label{sec:future}

\paragraph{Capture--recapture.} The self-report limitation has a known remedy.
Capture--recapture, standard in epidemiology and in software defect
estimation, requires only that overlap be recorded: for each error, whether
each detector found it independently. With two detectors, agent and human,
and an overlap count, the unobserved population becomes estimable. The
released log does not carry an overlap field. Adding one, and withholding
human-found errors from the agent for a fixed interval so that independent
detection has a chance to occur, is the change to the logging protocol we
would make first.

\paragraph{A confirmatory test of the absence hypothesis.} The comparison in
\S\ref{sec:mechanism} can become a test only if the grouping of classes is
fixed before the records it is applied to exist.

\paragraph{Independent classification and a control arm.} A re-classification
of the released log by someone other than the agent would address the
self-categorisation limit. A second run of the same task without an error log
would give the repeat rate something to be compared against.

\section{Conclusion}

An agent ran a real measurement process for three months and produced
forecasts with no demonstrated skill. That half of the result is dull. It was
also pre-registered, which is the only reason it could not later be reframed
as something better.

What the process recorded about itself is more useful. Most errors surfaced
within a day, but \LatGeSeven{} of \ErrN{} took a week or longer and the
slowest took \LatMax{} days. Close to half of them repeat an earlier record,
and detection did not get faster over the period. The failures that lasted
longest or recurred most were not wrong answers. They were rules that had been
written down and were then not applied, up to and including the rule that the
process should run at all.

Capability benchmarks answer how often an agent is right. An agent that
maintains something also needs its being wrong to become visible, and the
evidence here is that writing the lesson down does not make it so. Whether
that holds beyond one agent and one task is what this sample cannot say, which
is why the data is released and not only summarised.
